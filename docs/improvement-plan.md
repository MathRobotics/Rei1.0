本書は今後の実装順序を定める計画であり、未実装項目を対応済みとは扱わない。

## 現在の基準

- macOS ARM64のPython 3.11.14／3.13.1で各438テストが成功。
- RoboKotsはコミット `3f2673d7af58cd34f7af11686136241cdf905c91`、Pinocchioは4.1.0で検証。
- IK・軌道最適化・IOCのサンプルが動作。トルクの2階微分まで、NumPy／Rust、密行列／乗算、一括／逐次経路を検証。
- 比較した軌道問題はトルク項の重みが小さく、最適化も2反復。動力学主体の性能やIOC推定精度については結論を出していない。
- Python 3.12、他OS、ネイティブcyipoptは未検証。Python 3.11を最低対応バージョンとして維持する。

関連記録:
[Python互換性](../developer/benchmarks/python_compatibility.md)、
[バックエンド比較](../developer/benchmarks/pinocchio_rust_comparison.md)。

## 順最適化監査による追加課題（2026-09-23）

[監査結果](forward-optimality-audit.md)で、不等式境界のKKT診断がHinge残差を
使い、元の制約ヤコビアンを失う問題を再現した。最適性診断に影響するため、
符号付き余裕を評価する診断経路を追加して修正済み。ペナルティ問題の収束と実行可能性の表示の分離は今後の課題。
標準軌道例は一階・数値二階条件を満たしたが、一般の `converged` は局所最小・大域最小を保証しない。

## P0-1: 依存環境の再現性

現状は `uv.lock` がGit管理対象外で、RoboKotsの取得先が移動する `develop` ブランチ。
バージョン表記 `0.0.1` だけでは検証した実装を特定できない。

1. 開発・検証用の `uv.lock` をGit管理し、RoboKotsの `rev` を検証済みコミットへ固定する。
2. パッケージの依存範囲と開発用ロックを区別する。利用者向け依存を一律に完全固定しない。
3. 通常検証は `uv sync --locked` を用い、意図しない再解決を防ぐ。
4. 更新は別の変更として行い、コミット・依存差分・Python別テスト結果を記録する。
5. exFAT上の `.venv` で発生した問題を踏まえ、外付けドライブ利用時は内部ディスクの仮想環境とコピー方式を案内する。

## P0-2: CIと実ライブラリの検証

まず3.11／3.13を必須にし、3.12は追加検証で空白を埋める。
OS・Python・全オプションの直積を最初から必須にしない。

- 最小依存のジョブ: NumPy中心の本体と、バックエンド未導入時の動作を確認。
- 実ライブラリのジョブ: RoboKots、Rust拡張、Pinocchioをインストールし、統合テストを実行。
- 実ライブラリのジョブでは、必要な統合テストがスキップされた場合に失敗させる。モックによる置き換えも検知する。
- 既に確認したmacOS ARM64を基準に、利用可能なCIランナーでLinuxを追加。CI上の実行OSとCPUを結果に残す。
- cyipoptはネイティブ依存を含む独立ジョブとし、未実行時は未検証と表示する。
- ベンチマークは通常テストと分離する。共有ランナーの小さな時間差を合否判定に使わない。

完了時は、テスト結果に合格数・スキップ理由・Python・依存バージョン・RoboKotsコミットを残す。

## P1-1: IOCの数理的な妥当性

初回の[検証結果](ioc-validation.md): 正規化後係数のスケール変換を修正し、
識別性と制約未考慮の診断を追加。制約付きKKT推定と動的軌道の復元検証は引き続き未完了。

`estimate_ioc_weights()` は現在、項ごとの勾配行列を正規化し、単体上の最小ノルム問題を解く。
以下は監査・検証する項目であり、すべてを既知の不具合と断定するものではない。

1. **列正規化と重みの意味**
   `A_scaled = A * scales` に対する係数と、元の目的関数の係数を区別する。
   元スケールの係数は `scales * coefficients` に対応するため、必要な再正規化、戻り値の意味、両方の停留残差が整合するか検証する。
2. **制約付きの停留条件**
   等式制約下では許容方向への勾配射影または乗数を用いる。不等式には活動制約、乗数の符号、相補性を考慮する。
   `include_constraints` による項の選択だけで、制約付きIOCを正しく表現できると仮定しない。
3. **識別可能性**
   勾配行列の階数・特異値を確認し、ゼロ勾配や重複する目的項を区別する。
   重みが一意に決まらない例では、単一の推定値を正解として主張しない。
4. **既知重みからの復元**
   まず識別可能な小さな解析例、次にロボット軌道で検証する。
   複数軌道・ノイズ・目的項のスケール変更を含め、必要に応じて複数デモの勾配行列を積み重ねる。

完了条件: 解析例は既知解への誤差で、数値軌道は事前に設定した重み誤差・停留残差・再最適化時の軌道誤差で評価する。
閾値はデータと問題の条件数に基づいて定め、測定後に都合よく緩めない。

## P1-2: IOC専用サンプルと診断

既存の `stationarity_ioc.py` と時間比較用サンプルに加え、ロボットIOCを単独で理解できる例を用意する。

- 既知重みでのデモ生成 → 重み推定 → 推定重みで再最適化、の順に実行する。
- 使用した制約、重みの正規化、項の除外理由を表示する。
- 推定前後の重み、元スケール／正規化後の停留残差、識別性、軌道誤差を表示する。
- Pinocchio／RoboKotsを切り替え可能にし、両方に共通する目的項で比較する。
- 高階トルク微分など片方だけが対応する機能は別ケースにする。

P1-1で重みの意味を確定した後に実装する。既存の戻り値の意味を変更する場合は移行説明を付ける。

## P2: 性能測定と高速化

### 測定を先に拡張する

- 2／7自由度、軌道長、制御点数、動力学の評価間隔を変える。
- 位置中心、トルク主体、トルク微分、IOC、繰り返し窓更新を別ケースとして測る。
- モデル読込、コンパイル、制約削減、残差、ヤコビアン、JVP/VJP、最適化全体を分離する。
- 初回とウォームアップ後を区別し、中央値とばらつき、ピークメモリを記録する。
- モデル・入力・重力・収束条件を揃え、正確性を確認してから速度を比較する。
- 簡易 `7_dof_arm.urdf` は関節制限がなくPinocchioで読めない。実際の制限を定義するか、共通比較には検証済みFrankaを使う。

### プロファイルで確認できた箇所だけ改善する

候補は、コンパイル結果の再利用、一括評価、キャッシュ、JVP/VJPの利用、不要な密行列化の削減。
候補だけを根拠に大きな書き換えは行わない。

完了条件: 同じ環境と入力で改善を再現し、数値一致・収束結果・メモリ使用量に問題がないこと。
異なるマシンでの絶対時間や2反復だけの問題を根拠に、バックエンド全体の優劣を決めない。

## P3: API・配布・対応環境

- 外部ライブラリのAPI差分を `kots_api`／アダプタに集約し、サンプルや利用者が内部属性に依存する箇所を減らす。
- 重み・項選択・制約フラグ・収束状態の意味を、ソルバー間で一致させて文書化する。
- バックエンド未導入時の案内と、能力不足によるエラーを区別する。
- Python／バックエンドの対応表と依存更新手順を整備する。
- wheelをクリーン環境へインストールして本体・任意バックエンドの導入経路を確認する。

## 実施単位

1. 依存固定と更新手順。
2. CI導入と実ライブラリ検証の必須化。
3. IOCの正規化・制約・識別性の監査と回帰テスト。
4. 必要なIOC修正と専用サンプル。
5. ベンチマーク拡張。
6. 測定結果に基づく小さな性能改善。
7. API・配布の整備。

各変更では、問題・変更後の挙動・検証結果を残す。前段の失敗を後段の高速化で覆い隠さない。
新たな数値不整合や実ライブラリの互換性破損が見つかった場合は、この順序より修正を優先する。
